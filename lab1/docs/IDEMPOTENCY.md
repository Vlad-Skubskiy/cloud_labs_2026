# Ідемпотентність операцій запису

## Яку проблему це розв'язує

`POST /items` створює новий запис, тож **повтор запиту = дубль**. Повтори трапляються постійно й не залежать від «поганого» клієнта:

- клієнт не дочекався відповіді (таймаут), хоча сервер запит уже виконав, і повторив його;
- користувач випадково двічі натиснув кнопку;
- проксі/SDK автоматично ретраїть запит;
- мережа обірвалася після виконання, але до отримання відповіді.

Клієнт у цих випадках **не може знати**, чи був запис створений. Заголовок `Idempotency-Key` дозволяє безпечно повторювати: «ось унікальний ідентифікатор мого наміру; якщо ти його вже виконував — просто віддай ту саму відповідь».

## Контракт

Клієнт генерує унікальний ключ (наприклад, UUID) **на один намір** і надсилає його в кожній спробі:

```bash
curl -X POST "$URL/items?name=milk" -H "Idempotency-Key: 7d1c5a52-0f3e-4a64-b6a9-2f6e6f1d9c11"
```

| Ситуація | Відповідь |
|---|---|
| Перший запит із ключем | виконується; результат зберігається в Redis на **24 год** |
| Повтор із тим самим ключем і тими ж параметрами | **та сама** відповідь (статус і тіло), операція не виконується; додається заголовок `Idempotent-Replay: true` |
| Повтор, поки перший ще виконується | `409 Conflict` + `Retry-After: 1` |
| Той самий ключ, але інші `name`/`description` | `422` (ключ не можна перевикористовувати для іншого запиту) |
| Некоректний ключ (порожній, > 255 символів) | `400` |
| Redis недоступний | `503` + `Retry-After` (з ключем гарантію дати не можна, тому не виконуємо) |
| Заголовка немає | запис **не** ідемпотентний, як і раніше |

## Як працює (`idempotency.py`)

Запис у Redis `idem:POST:/items:<key>`:

1. `SET key {"state":"processing","fp":<sha256 параметрів>} NX EX 60` — **атомарно** «займає» ключ. Якщо два запити прийшли одночасно, `NX` пропустить рівно один; інший отримає `409`.
2. Власник ключа виконує операцію.
3. `SET key {"state":"done", status, body, headers} EX 86400` — зберігає результат на 24 год.
4. Якщо виконання кинуло виняток — `DEL key`, щоб клієнт міг повторити.

`processing` живе лише 60 с: якщо інстанс помер посеред операції, ключ не блокує клієнта на добу.

## Як це поєднується із завданням 6?

У async-режимі «результат» першого запиту — це `202` із `job_id`. Ідемпотентність діє на **двох рівнях**, і кожен закриває свою діру:

| Рівень | Що гарантує | Від чого захищає |
|---|---|---|
| 1. `Idempotency-Key` у API (Redis) | повтор запиту → той самий `job_id`, **у чергу йде одне повідомлення** | клієнтські ретраї, подвійний клік |
| 2. `job_id` UNIQUE у БД (воркер) | повторна обробка одного повідомлення → **один запис** | at-least-once доставка SQS (воркер упав до `DeleteMessage`, timeout видимості) |

Рівні зв'язані: `job_id = uuid5("idempotency:" + key)` — тобто **виводиться з ключа детерміновано**. Завдяки цьому закрито й вузьке вікно між «повідомлення вже в черзі» і «результат ще не збережено в Redis»: якщо в цей момент API впаде і клієнт повторить запит, у чергу піде друге повідомлення, але з **тим самим `job_id`**, і воркер відсіче його на рівні БД. Без цього зв'язку Redis-ідемпотентність не вберегла б від дубля в цьому вікні.

Разом: клієнтські повтори не множать повідомлення, а повторні доставки повідомлень не множать записи. Це і є «ефективно рівно один раз» поверх at-least-once.

## Обмеження

- **Ключ і evict у Redis.** ElastiCache за замовчуванням `volatile-lru`: при нестачі пам'яті ключі з TTL (а наші мають TTL) можуть бути витіснені раніше за 24 год. Тут Redis спільний із кешем списку. Для продакшену ідемпотентність варто тримати в окремому інстансі з `noeviction` або в самій БД. Рівень 2 (UNIQUE job_id) лишається страховкою від дублів запису.
- **Область ключа.** Ключ глобальний для ендпоінта, бо в застосунку немає автентифікації. У реальному API ключ має складатися з `user_id + key`.
- **Sync-режим** теж використовує `job_id`, виведений з ключа, тож і там дубль у вікні «записав, але не зберіг у Redis» відсікається БД.
- Redis — точка відмови для запису з ключем (відповідь `503`) — свідомо: краще відмовити, ніж мовчки порушити гарантію.
