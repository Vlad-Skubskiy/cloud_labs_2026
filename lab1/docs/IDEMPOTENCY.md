# Ідемпотентність операцій запису

## Яку проблему це розв'язує

`POST /items` створює новий запис, тож **повтор запиту = дубль**. Повтори трапляються постійно й не залежать від «поганого» клієнта:

- клієнт не дочекався відповіді, хоча сервер запит уже виконав, і повторив його;
- користувач випадково двічі натиснув кнопку;
- проксі/SDK автоматично ретраїть запит;
- мережа обірвалася після виконання, але до отримання відповіді.

Клієнт у цих випадках **не може знати**, чи був запис створений. Заголовок `Idempotency-Key` дозволяє безпечно повторювати: «ось унікальний ідентифікатор мого наміру; якщо ти його вже виконував — просто віддай ту саму відповідь».

## Idempotency-Key

Клієнт генерує унікальний ключ (наприклад, UUID) **на один намір** і надсилає його в кожній спробі:

```bash
curl -X POST "$URL/items?name=milk" -H "Idempotency-Key: 7d1c5a52-0f3e-4a64-b6a9-2f6e6f1d9c11"
```

| Ситуація | Відповідь |
|---|---|
| Перший запит із ключем | виконується; результат зберігається в Redis на **24 год** |
| Повтор із тим самим ключем і тими ж параметрами | **та сама** відповідь (статус і тіло), операція не виконується; додається заголовок `Idempotent-Replay: true` |
| Повтор, поки перший ще виконується | `409 Conflict` + `Retry-After: 1` |
| Той самий ключ, але інші `name`/`description` | `422` (ключ не можна перевикористовувати для іншого запиту) |
| Некоректний ключ (порожній, > 255 символів) | `400` |
| Redis недоступний | `503` + `Retry-After` (з ключем гарантію дати не можна, тому не виконуємо) |
| Заголовка немає | запис **не** ідемпотентний, як і раніше |

## Як працює (`idempotency.py`)

Запис у Redis:

1. Займає ключ. Якщо два запити прийшли одночасно, прапорець Not Exist пропустить рівно один; інший отримає `409`.
2. Власник ключа виконує операцію.
3. `SET key {"state":"done", status, body, headers} EX 86400` — зберігає результат на 24 год.
4. Якщо виконання кинуло виняток — ключ видаляється, щоб клієнт міг повторити.

`processing` живе лише 60 с: якщо інстанс помер посеред операції, ключ не блокує клієнта на добу.

## Як це поєднується із завданням 6?

1. Без ключа повтор отримав би нові id і створив друге повідомлення — worker вважав би його іншим показанням. З ключем повтор отримує той самий 202 з тим самим id, а в черзі лишається одне повідомлення.
2. SQS може доставити повідомлення двічі; ідемпотентний worker другу копію ігнорує, бо id той самий.

## Тест



Локально — окремий тестовий Postgres на порту `5433` і Redis із compose (`6379`). Окрема БД потрібна, бо тести пишуть рядки в `items`:

```bash
docker run -d --rm --name test-pg -p 5433:5432 \
  -e POSTGRES_USER=test -e POSTGRES_PASSWORD=test -e POSTGRES_DB=test postgres:15-alpine
docker compose up -d redis

DATABASE_URL=postgresql+psycopg://test:test@localhost:5433/test \
REDIS_URL=redis://localhost:6379/0 pytest -v

docker stop test-pg
```

| Тест | Що доводить |
|---|---|
| `test_sync_same_key_one_row_two_identical_responses` | два однакові запити, **в БД один рядок** |
| `test_without_key_every_request_writes` | без ключа два запити → два рядки |
| `test_async_same_key_one_message_and_duplicate_delivery_is_harmless` | два запити → одне повідомлення в черзі; те саме повідомлення, оброблене воркером двічі → один рядок |
| `test_same_key_different_payload_is_rejected` | 422 |
| `test_concurrent_requests_with_same_key_write_once` | два **паралельні** запити → один виконався, інший `409`; в БД один рядок |


## Обмеження

- ElastiCache за замовчуванням при нестачі пам'яті ключі з TTL можуть бути витіснені раніше за 24 год. Тут Redis спільний із кешем списку. Для продакшену ідемпотентність варто тримати в окремому інстансі з `noeviction` або в самій БД.
- Ключ глобальний для ендпоінта, бо в застосунку немає автентифікації. У реальному API ключ має складатися з `user_id + key`.
- **Sync-режим** теж використовує `job_id`, виведений з ключа, тож і там дубль у вікні «записав, але не зберіг у Redis» відсікається БД.
- Redis — точка відмови для запису з ключем (відповідь `503`). краще відмовити, ніж мовчки порушити гарантію.
