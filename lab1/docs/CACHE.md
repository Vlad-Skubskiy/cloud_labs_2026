# Кешування читання (ElastiCache Redis)

Код: [cache.py](../cache.py), використання — `GET /items` у [main.py](../main.py). Інфраструктура: [terraform/elasticache.tf](../terraform/elasticache.tf) (`cache.t3.micro`, Redis 7.1).

## Як працює

- Патерн **cache-aside**: `GET /items` шукає ключ `items:v<version>:list:<limit>:offset:<offset>`. На HIT повертає готовий JSON без звернення до БД, на MISS читає PostgreSQL і кладе відповідь у Redis.
- **TTL = 30 с** (`CACHE_TTL_SECONDS`) плюс випадковий jitter 0–3 с (10 % TTL). Jitter потрібен, щоб ключі не закінчувалися одночасно і не було хвилі запитів до БД (cache stampede).
- **Інвалідація при записі** (`CACHE_INVALIDATE_ON_WRITE`, за замовчуванням вимкнена): після вставки воркер (або API в режимі `sync`) робить `INCR items:version`. Наступні читання йдуть на новий ключ, а старі ключі просто доживають свій TTL.
- Redis недоступний → таймаут 250 мс, запит іде в БД. Кеш не є точкою відмови.
- Заголовок відповіді `X-Cache: HIT | MISS | BYPASS`; `?nocache=true` обходить кеш.
- Кешується лише список `GET /items`. `GET /items/{id}` завжди читає БД.

## Методика порівняння

Два прогони Locust з однаковими параметрами (див. [LOADTEST.md](LOADTEST.md)):

1. **Без кешу:** у task definition (`terraform/ecs.tf` → `environment`) тимчасово додати `{ name = "CACHE_ENABLED", value = "false" }`, `terraform apply`, дочекатися нового деплою, запустити тест.
2. **З кешем:** прибрати змінну, `terraform apply`, скинути лічильники, запустити тест, зняти статистику:

   ```bash
   curl -X DELETE "$URL/cache/stats"   # перед тестом
   curl "$URL/cache/stats"             # після тесту → hits, misses, hit_ratio
   ```

Навантаження на базу береться з дашборду `notes-dashboard`: `RDS CPUUtilization` (Average) і `DatabaseConnections` (Maximum) за час тесту. Додатково — `ReadIOPS` в метриках RDS.

## Скільки часу клієнт може бачити застарілі дані

Поточна конфігурація в AWS: TTL 30 с, інвалідація вимкнена, запис асинхронний.

**Застарілість ≤ TTL + jitter ≈ 33 с** від моменту, коли запис з'явився в БД. Найгірший випадок: ключ закешовано за мить до коміту нового item, і він живе ще 30 + 3 с. До цього додається затримка черги (від `POST` до коміту воркером — зазвичай мілісекунди–секунди, при великій черзі довше; див. [QUEUE.md](QUEUE.md)). Але вона існує й без кешу.

Redis спільний для всіх задач API, тож різні задачі бачать ту саму версію. Розбіжностей між інстансами немає.

## Як зменшити цей час

1. **Інвалідація при записі** — вже реалізована, вмикається `CACHE_INVALIDATE_ON_WRITE=true` в `environment` задач API та воркера. Після коміту воркер робить `INCR items:version`, тож уже наступний `GET /items` іде повз старий ключ. Застарілість падає практично до 0 (від коміту), TTL лишається запобіжником. Ціна — нижчий hit ratio за частих записів: одна вставка скидає весь список.
2. **Менший TTL** (наприклад, 5 с). Межа застарілості пропорційно падає, але частіші промахи збільшують навантаження на БД. Компроміс між свіжістю і розвантаженням.
3. **Read-your-writes на клієнті.** Після `POST` клієнт показує власний запис з відповіді (`GET /jobs/{id}` → `item_id`) і не чекає, поки той з'явиться у списку. Або читає з `?nocache=true` одразу після свого запису.
4. **Write-through / точкове оновлення.** Воркер після вставки оновлює закешований список сам, замість того щоб його скидати. Свіжість і hit ratio зберігаються, але логіка складніша і з'являються гонки між паралельними записами.
