# Кешування читання (ElastiCache Redis)

Найважча операція читання — статистика показань GET /items — працює за схемою cache-aside зі спільним Redis.

## Як працює

- `GET /items` шукає ключ `items:v<version>:list:<limit>:offset:<offset>`. На HIT повертає готовий JSON без звернення до БД, на MISS читає PostgreSQL і кладе відповідь у Redis.
- **TTL = 30 с** плюс випадковий jitter 0–3 с. Jitter потрібен, щоб ключі не закінчувалися одночасно і не було хвилі запитів до БД.
- Redis недоступний → таймаут 250 мс, запит іде в БД.
- Кешується лише список `GET /items`. `GET /items/{id}` завжди читає БД.

## Методика порівняння

Два прогони Locust з однаковими параметрами (див. [LOADTEST.md](LOADTEST.md)):

1. **Без кешу:** у task definition (`terraform/ecs.tf` → `environment`) тимчасово додати `{ name = "CACHE_ENABLED", value = "false" }`, `terraform apply`, дочекатися нового деплою, запустити тест.
2. **З кешем:** прибрати змінну, `terraform apply`, скинути лічильники, запустити тест, зняти статистику:

   ```bash
   curl -X DELETE "$URL/cache/stats" 
   curl "$URL/cache/stats"             
   ```

## Скільки часу клієнт може бачити застарілі дані

Поточна конфігурація в AWS: TTL 30 с, інвалідація вимкнена, запис асинхронний.

**Застарілість ≤ TTL + jitter с** від моменту, коли запис з'явився в БД. Найгірший випадок: ключ закешовано за мить до коміту нового item, і він живе ще 30 + 3 с. До цього додається затримка черги (від `POST` до коміту воркером — зазвичай мілісекунди–секунди, при великій черзі довше;. Але вона існує й без кешу).

Redis спільний для всіх задач API, тож різні задачі бачать ту саму версію. Розбіжностей між інстансами немає.

## Як зменшити цей час

1. **Інвалідація при записі** — Після коміту воркер робить `INCR items:version`, тож уже наступний `GET /items` іде повз старий ключ. Застарілість падає практично до 0, TTL лишається запобіжником. Але стає нижчим hit ratio за частих записів: одна вставка скидає весь список.
2. **Менший TTL** (наприклад, 5 с). Межа застарілості пропорційно падає, але частіші промахи збільшують навантаження на БД.

3. **Write-through / точкове оновлення.** Воркер після вставки оновлює закешований список сам, замість того щоб його скидати. Свіжість і hit ratio зберігаються, але логіка складніша і з'являються Race Condition.
